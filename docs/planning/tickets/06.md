## What to build

Synchronize completed sales with safe acknowledgements and account recovery. Deliver the complete staff/customer behavior below with the necessary persistence, business rules, API, usable Arabic UI and verification. The approved parent specification is authoritative.

## Acceptance criteria

- [ ] Startup, reconnect and manual retry submit durable completed records with stable operation identities. Server atomically deduplicates and returns acknowledged IDs with an associated stock snapshot/version.
- [ ] Rebase remaining local effects atomically; a lost response, repeated sync or two tabs cannot deduct twice, resurrect a sold unit or expose another account queue.
- [ ] Revalidate identity/branch grants on reconnect. Disabled accounts cannot begin new connected work; earlier completed sales remain recoverable with manager assistance. Expired sessions can reauthenticate without losing work; client timestamp alone is not authorization proof.
- [ ] Preserve late completed sales, use available FIFO units without stealing confirmed allocations, and expose unallocated remainder/cost incompleteness for manager reconciliation. Never invent zero/average costs or silently delete the completed sale.
- [ ] Exercise interruption, multiple tabs, snapshot races, revoked/expired sessions and prior-account queue privacy through real browsers plus concurrent real PostgreSQL HTTP tests.
- [ ] Run the established typecheck, architecture, relevant behavior tests and build gates; preserve existing checks and record verification. No application test is considered passed merely because it is written.
