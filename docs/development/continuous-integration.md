# Repository continuous integration

`.github/workflows/ci.yml` defines repeatable verification for pull requests into `main` and pushes to `main`. It is a local candidate until committed and published; preparing this file does not activate GitHub Actions or prove a hosted run passed. Publishing it, changing repository settings or branch protection, and deployment are separate actions.

Every job uses a fresh GitHub-hosted Ubuntu 24.04 x64 runner, Node 22.23.3, pnpm 10.34.5 and `pnpm install --frozen-lockfile`. The pnpm version and Node support minimum agree with root `package.json`; update these workflow pins deliberately when changing the project runtime. The October 9, 2026 refresh selects the patched Node 22 runtime without changing its major version; older Node 22.13.1 results remain dated historical evidence. The actions themselves use GitHub's Node 24 action runtime, independently of the project's Node 22 runtime.

## Required jobs

| Job | Commands and coverage |
| --- | --- |
| Types, architecture, scripts and builds | Verify runtime pins; `pnpm audit --prod --audit-level=moderate`; `pnpm typecheck`; `pnpm check:architecture`; `node --check scripts/measure-storefront-performance.mjs`; `node --test tests/scripts/storefront-performance.test.mjs tests/scripts/check-bundles.test.mjs` for the performance helper and actual bundle guard regressions; `pnpm build` for all three applications and the existing bundle-separation check. |
| PostgreSQL and HTTP integration | `pnpm test:http`, using the entire `tests/http` suite selected by `vitest.config.ts`, including migration and branch-inventory migration coverage. |
| Chromium browser acceptance | `pnpm exec playwright install --with-deps chromium`, then `pnpm test:browser --reporter=line` with all tests selected by `playwright.config.ts`. |

The HTTP and browser jobs start only after the static/build job succeeds, and run on separate machines. Vitest already disables file parallelism and Playwright uses one worker. No check is marked `continue-on-error`; no CI grep filter, test exclusion or retry override is added. Failures retain their ordinary nonzero status in GitHub logs. A newer run cancels obsolete work for the same pull request or branch.

The production-dependency audit runs immediately after locked installation using pnpm 10.34.5. It queries current registry advisories rather than freezing advisory data with the lockfile; results can change for identical source and dependency versions. Moderate, high and critical findings fail this required job. Registry failures also fail it: the workflow adds no ignore list, `--ignore-registry-errors`, `--ignore-unfixable`, `--fix` or automatic lockfile mutation. The command and flags follow [pnpm's version 10 audit documentation](https://pnpm.io/10.x/cli/audit). A passing local audit records the advisory state at its execution time; it does not prove a hosted run passed or guarantee that later advisories will remain clear.

## Isolation and portability

The workflow needs no repository secret, external PostgreSQL service, `.env` file, real staff credentials, recovery provider or production database URL. `packages/testkit/src/postgres.ts` creates new temporary embedded PostgreSQL clusters; the integration files create their own databases. `scripts/e2e-stack.ts` creates a separate `bravos_e2e` database, test-only accounts, API on loopback port 3011 and local recovery/media directories. Playwright starts Vite on 5174 and Next development mode on 3001 with `reuseExistingServer: false`. Its control-file teardown stops the API and database it owns. Disposable runner storage isolates those directories from business data and other jobs.

Linux requires the locked `@embedded-postgres/linux-x64` optional package and its symlink-hydration postinstall. This candidate adds its name to root `pnpm.onlyBuiltDependencies` and the duplicated `.npmrc` allowlist, alongside the existing Windows package; this permission change needs no dependency version or lockfile change. In pnpm 10.34.5, root manifest build settings override the earlier npm configuration, and workspace settings can then override those values; the current workspace manifest supplies no competing build policy. Both repository allowlists now agree on this Linux package. The precedence was checked against [pnpm's pinned config source](https://github.com/pnpm/pnpm/blob/v10.34.5/config/config/src/index.ts), and the required postinstall against the [official source for the locked PostgreSQL version](https://github.com/leinelissen/embedded-postgres/blob/9a1e52f4ac4d92bf24976f635020374342fd0838/packages/linux-x64/package.json). Do not install with `--no-optional`, suppress all dependency scripts, run the test harness as root, or replace it with a live database to bypass a failed initialization. The workflow uses the runner's ordinary user; Playwright's documented `--with-deps` step installs browser OS libraries separately. This Linux runner choice is based on the package's supported platform and the current source; a successful hosted run is still required to verify the full combination.

`scripts/pinned-env.ts` prepends the local-tool path and the directory of `process.execPath`, then preserves the incoming `PATH`. Child processes therefore use the same Node runtime on Windows or Linux, including a checksum-verified portable Windows copy or the Node installed by Actions. Storefront fonts use `next/font/local`, with exact filenames checked into `apps/storefront/app/fonts`. The PDF renderer resolves the checked-in Cairo font, and `scripts/build-api.mjs` copies it into the built API assets. No Google Fonts download or Windows system-font path is required.

The complete browser suite also invokes built internal-app previews in `offline-production.spec.ts` and `production-login.spec.ts`. Declaring this suite in CI is not evidence that those preview launches were permitted or executed locally. The storefront browser server remains Next development mode: this workflow does not provide a production storefront performance comparison, hosted TLS checks, a physical-device check or a production release rehearsal. The pure performance-script tests open no browser or server. Follow [storefront-performance.md](storefront-performance.md) for the separate permitted isolated-production measurement procedure; a rejected launch must be resolved, not worked around through CI.

The existing reporting browser scenario skips itself only when its timeout window would cross Cairo midnight. Review skipped counts in each run and rerun that scenario outside the boundary before claiming complete reporting coverage. This workflow does not add or expand that guard. The repaired `scripts/scratch-migrate.ts` now expects migrations 001–035. Its isolated local `pnpm migrate:scratch` verification passed all 35 migrations, the 014–035 down/reapply sequence and failure rollback on 2026-10-07; the verified source SHA-256 was `74D4205FE33FA4039CA9A82064E531618EEA8796D32AFE6B20A86609D873A226`. This separate local probe is not a workflow step: the current HTTP migration suite remains a required CI gate. Neither the local probe result nor its source hash proves hosted CI execution.

## Permissions and maintenance

The workflow grants only `contents: read`, disables persisted checkout credentials and uses `pull_request` rather than `pull_request_target`. It does not reference secrets or production environments, write repository data, cache dependencies or credentials, publish artifacts, call release tooling or deploy. Fork pull requests may still require GitHub's normal maintainer approval under repository settings. No remote workflow run or setting change is part of local preparation.

Record actual command results separately from this declared coverage. YAML review, command existence, a successful local Windows build or a subset of tests cannot substitute for a successful Ubuntu GitHub run of all required jobs.
