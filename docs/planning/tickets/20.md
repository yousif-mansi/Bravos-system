## What to build

Confirm WhatsApp-agreed online orders with protected FIFO allocations. Deliver the complete staff/customer behavior below with the necessary persistence, business rules, API, usable Arabic UI and verification. The approved parent specification is authoritative.

## Acceptance criteria

- [ ] Assigned representative and manager backup inspect pending requests, record contact attempts and customer-agreed basket revisions retaining original request details; ordinary cashiers cannot change order stages.
- [ ] Before confirmation require verification that actual items were located and physically set aside. Recheck agreed quantities/prices, atomically confirm with FIFO allocation, stock deduction and coupon usage once.
- [ ] Pending requests yield to physical sales; later shortages require WhatsApp agreement without silent substitutions. Concurrent confirmations/POS cannot double-allocate a unit; already physically completed cash sale remains recorded with any unallocated discrepancy.
- [ ] Support manual unreachable cancellation only after configurable 48-hour default and at least 2 attempts with reason; no automatic pending cancellation or confirmed expiry.
- [ ] Test races/rollback/coupon limits/role boundaries and unchanged confirmed prices via real concurrent PostgreSQL HTTP operations and a representative UI workflow.
- [ ] Run the established typecheck, architecture, relevant behavior tests and build gates; preserve existing checks and record verification. No application test is considered passed merely because it is written.
