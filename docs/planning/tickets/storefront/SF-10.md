# SF-10 — Calm Arabic COD checkout

**Phase:** 4. **Status:** Approved; awaiting dependencies and content gates. **Blocked by:** SF-09.  
**Outcome:** Mobile customers understand required details, the authoritative COD amount and what happens after sending a request.

## Scope and files

- Existing: `apps/storefront/app/checkout/page.tsx` rendering/copy/accessibility, including bounded field-feedback presentation state driven by native `onInvalid` and input correction. Do not change validation rules or submission eligibility.
- Proposed: adjacent `checkout-form.tsx`, `checkout-summary.tsx`, `checkout-status.tsx`, `checkout.module.css` only as presentational extractions if helpful.
- Tests: `tests/browser/checkout.spec.ts`; HTTP checkout suite is regression evidence, not new business implementation.
- Keep validation decisions, quote keys, effects, storage helpers, exact request persistence, operation ID and submission/recovery paths unchanged.

## Acceptance criteria

- [ ] Arabic form clearly separates required name/mobile/area/address from optional alternate phone/landmark/notes; correct labels and mobile input affordances preserve validation rules.
- [ ] Existing native required-field validation gains visual feedback, `aria-invalid`, associated error IDs/guidance and focus. Track presentation state from native invalid events and clear it appropriately on correction; values remain after errors. No new validation policy or parallel custom validator.
- [ ] Merchandise, discounts/coupon, configured delivery fee and final COD total are bound to existing authoritative quote values. No client recomputation or fee assumption.
- [ ] Cart/area/coupon changes still invalidate a reviewed quote; stale in-flight responses cannot be accepted. Existing submission eligibility is unchanged.
- [ ] Clear distinction between reviewing price, submitting, uncertain response, recovery, ordering closed, and successful pending request. Success provides reference and later WhatsApp confirmation, not a paid/stock-reserved claim.
- [ ] Retry uses the persisted exact operation/request and preserves later cart additions. Never replace uncertain-submit recovery with a generic fresh POST retry.
- [ ] Quiet shell, no campaign motion/upsell, no keyboard or sticky-summary obstruction. Loading says `لحظات...`; failures explain next safe action.
- [ ] Missing configured delivery areas renders the existing unavailable path clearly, with no hard-coded fallback fee/area.

## Verification and risks

Typecheck; full focused checkout Playwright suite: mobile fields/focus, quote totals, changed fees/stock, response loss/same-operation recovery, ordering closed and retained newer cart items. Real test PostgreSQL with isolated delivery-area fixtures. Risk: this page is a state machine despite being one file; diff must show presentation-only edits, with guards/effects/helpers preserved. No refactor for preference.
