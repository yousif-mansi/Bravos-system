## What to build

Correct erroneous saved sales and Returns while preserving actual effects. Deliver the complete staff/customer behavior below with the necessary persistence, business rules, API, usable Arabic UI and verification. The approved parent specification is authoritative.

## Acceptance criteria

- [ ] Manager corrects/cancels a saved erroneous sale or posted return using an original linked record, required correction reason and actor/time. No hard deletion or employee access.
- [ ] Ask for/record the actual merchandise and cash correction facts; cancellation alone does not prove goods came back or money was refunded. Customer returns remain in the dedicated workflow.
- [ ] Derive effective quantities/amounts from prior effects and intervening returns/allocations. Changing a paid record neither pays again nor claims cash recovered automatically; retries apply once.
- [ ] Provide original/effective detail views and test real recording-error examples, existing return/payment relationships, duplicate correction and authorization through HTTP without weakening original-history assertions.
- [ ] Run the established typecheck, architecture, relevant behavior tests and build gates; preserve existing checks and record verification. No application test is considered passed merely because it is written.
