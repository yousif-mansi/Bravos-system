## What to build

Keep cached POS and completed cash sales durable during outages. Deliver the complete staff/customer behavior below with the necessary persistence, business rules, API, usable Arabic UI and verification. The approved parent specification is authoritative.

## Acceptance criteria

- [ ] An already signed-in cashier can use cached catalog/selling prices, edit a cart and complete a physical cash sale offline; no fresh offline login, receiving, Returns, expense posting or permission changes are offered.
- [ ] Persist completed sale, paid values, actor/branch and outbox entry in one IndexedDB transaction before displaying saved success. Network calls stay outside it. Storage failure is visible without falsely reversing exchanged goods/cash or claiming a saved sale.
- [ ] Persist local stock effects and reject known over-quantity including repeated rows. Show unsynchronized counts and queued sale details only to the permitted account.
- [ ] Precache the entire essential POS path before offline readiness; preserve completed records across restart/logout and versioned storage/application updates. Never clear a different account queue. Provide safe update deferral when migration cannot preserve work.
- [ ] Prove outage/restart/storage failure/account switching in a real browser using real IndexedDB; no mock-storage tests can substitute for this gate. Promotion cache evaluation is extended by ticket 11.
- [ ] Run the established typecheck, architecture, relevant behavior tests and build gates; preserve existing checks and record verification. No application test is considered passed merely because it is written.
