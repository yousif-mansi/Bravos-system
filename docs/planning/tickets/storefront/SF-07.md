## Acceptance criteria

- [x] Desktop commerce rail stays visible where viewport height permits; on constrained height it remains scrollable/reachable rather than clipping controls. Mobile bar respects safe area and page bottom spacing.
- [x] Both presentations use the existing single selected-variant/quantity state and add callback. One interaction adds once; no duplicate forms, state owners or analytics emissions.
- [x] Exact selected variant price is visible. Labeled size/color choices resolve existing IDs; unavailable combinations remain disabled, with textual states and no invented swatch colors.
- [x] Existing initial selection, quantity caps, cart-aware remaining quantity and orderable gates remain unchanged. Coming Soon/Out of Stock do not gain an enabled action.
- [x] Mobile bar shows price, selected size/color summary, an accessible path to change selection and the same add action. It never covers errors, focused controls or meaningful content.
- [x] Successful add gives immediate, visible and announced non-blocking feedback with a cart link; count updates through existing cart state. Failure feedback is distinct and actionable.
- [x] Existing size guide is reachable; do not fabricate material data or couple gallery changes to variants without API support.

## Verification and risks

Typecheck; existing quantity/variant/aggregated persistent-cart browser tests plus exact-price changes, one-click-one-add, disabled combinations, sticky overlap and keyboard checks. Risk: two visual purchase surfaces can accidentally duplicate state/actions. Keep state and all validation in the existing purchase-panel owner; review diff for behavior changes.
